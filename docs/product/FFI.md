# Ink — граница Go (FFI)

**Статус:** граница Go, как она реализована в 0.2; §10 — открытые решения.
**Связано:** [syntax.md](../../vault/features/syntax.md), [SPEC.md](SPEC.md), [PAR.md](PAR.md),
[EDGES.md](EDGES.md), [decisions.md](../maintain/decisions.md).

## 0. Короткая граница для агента

- Прямой `use` Go-пакета — норма: `net/http`, `encoding/json`, `os/exec`,
  `crypto/*`, `database/sql` + `modernc.org/sqlite`, `golang.org/x/sys/unix`,
  `x/sys/windows`, `bubbletea`, `raylib-go`, `go-wlroots`.
- Локальный Go-пакет — **binding**, а не app-код. Он нужен только если Ink не
  может выразить API: cgo/`import "C"`, `unsafe`/ABI, сырой `ioctl`, COM/OLE,
  Cocoa/ObjC, JNI, lifecycle-обвязка с callback/ctx, generic/variadic
  interface conformance, value-receiver интерфейсы, `chan`/`select`.
- `go:embed` не требует Go: `ink build -embed dir` + `asset(path)`.
- Замок не требует Go: `serve obj;` (type-wide, без пользовательского Go).
- Горячий цикл не требует Go: Ink компилируется в тот же Go-runtime; сначала
  измерение и арена/кодогенератор, потом отдельный Go-kernel.
- C-библиотека: сначала ищи готовый Go-binding; свой адаптер — один раз на
  зависимость, не на фичу. Держи его в `bindings/` или `ffi/`, facade — в Ink.

## 1. Позиция

Ink не заменяет Go runtime и экосистему. Он компилируется в Go, живёт на
Go scheduler/GC и вызывает Go-пакеты. Это не временное решение, а основа
языка.

Обратная сторона: Go не должен стать вторым языком приложения. Если
`context.Context`, `*http.Client`, `sync.Mutex` и `if err != nil` расходятся
по домену, Ink превращается в Go с точками с запятой. Граница должна быть
явной и узкой.

Правило:

- **Go runtime/ecosystem остаётся.**
- **Raw Go — foreign layer и escape hatch.** Он живёт в адаптере, а не в
  app-коде.
- **App-код видит простой Ink API.** Если ему нужен Go-тип, чтобы
  работать, граница проведена неправильно.

«Foreign layer» — это место, а не настроение: один каталог, один владелец,
один API. Если один и тот же сложный Go-пакет импортируется из нескольких
app-файлов, границы уже нет.

Escape hatch тоже живёт здесь. В Ink нет `unsafe`-блока или «доверенной
секции» внутри функции: если для задачи нужен raw Go, код переезжает в
`bindings/` или `ffi/`, а app-код продолжает видеть Ink API. Это дороже
одной строки `use`, но именно поэтому граница остаётся видимой.

Это архитектурная граница, не sandbox. Go-код доверенный и может делать всё,
что может Go; FFI не защищает от вредной библиотеки.

## 2. Слои

| Слой | Что это | Что можно | Что нельзя |
|---|---|---|---|
| App | домен и UI на Ink | Ink-типы, `?`, `on err`, `par` (включая `spawn f()`) | `context.Context` без нужды, Go-интерфейсы и указатели в публичном API, `sync`/`atomic`, `chan`/`select` |
| Facade | Ink-модуль с простым API | `use` Go-пакета внутри, маппинг типов | протаскивать Go-типы в сигнатуры |
| Binding | Go-пакет для сложной библиотеки | всё, что нужно Go: ctx, goroutines, callbacks, locks | попадать в app-код напрямую |
| Generated | `zz_ink.go`, `.ink/runtime` | генерируется компилятором | править руками |

Рекомендуемая раскладка:

```text
app/
  main.ink
  domain/user.ink
  ffi/httpc.ink          // facade: единственный файл, знающий про httpc
  bindings/httpc/        // Go-пакет, только если facade не справляется
    client.go
```

App импортирует `./ffi` (или `./domain`), а не `bindings/httpc`. Go-пакет
может быть отдельным модулем, если у него свой жизненный цикл и версии; для
локальной разработки — `replace` в `go.mod`.

### 2.1. Когда хватает прямого `use`

Прямой `use` Go-пакета — не грех. Это норма для leaf-функций:

```hare
use fmt;
use strings;
use sort;
```

Критерии «простой библиотеки»:

- нет lifecycle (open/close, start/stop);
- нет callbacks и событий;
- нет `context.Context` и фоновых goroutine;
- нет глобального состояния и `init`, на которое нельзя повлиять;
- типы из библиотеки не входят в публичные сигнатуры домена;
- ошибки не требуют классификации по типу.

Если хотя бы один пункт не выполняется — нужен facade. Если библиотека
сложная по своей природе (сетевой клиент, БД, UI-тулкит, драйвер) — facade
плюс, скорее всего, Go-binding.

### 2.2. Когда нужен Go-binding, а не Ink-facade

Ink-facade достаточно, если маппинг — это тонкая обёртка: вызвать
функцию, переложить поля, вернуть `T!`. Go-binding нужен, когда:

- библиотека держит callbacks и вызывает их из своих goroutine;
- нужен `context.Context` внутри binding: дедлайн, отмена, фоновая goroutine;
- есть generics, variadic-интерфейсы или value-receiver интерфейсы;
- нужна своя модель locking/atomic;
- нужно управлять lifetime (регистрация/отмена подписки, пул, reconnect);
- ошибки надо превратить в устойчивый Ink-enum, а не в строки.

Binding — обычный Go-пакет с маленьким API, спроектированным под Ink.
Он может позволить себе Go-идиомы, потому что его никто, кроме facade, не
видит.

## 3. Правила facade

### 3.1. Сигнатуры

Публичный API facade состоит из Ink-типов:

- `str`, `bool`, числа, `T[]`, `T[N]`, `map[K, V]`, `*T`, `fn(...)`, `error`;
- struct/enum, объявленные в Ink;
- opaque handle — struct с unexported полем Go-типа.

В публичной сигнатуре допустим `context.Context`, когда функция передаёт его
в Go-API или выводит deadline; хранить его в struct нельзя. Запрещено:

- Go-интерфейс (`http.RoundTripper`, `io.Reader`) как параметр/результат;
- Go-указатель (`*http.Client`, `*sql.DB`) как параметр/результат;
- `func`/`chan`/`select`-типы;
- имена codegen (`_s_*`, `zz_ink.go`).

Opaque handle выглядит так:

```hare
use context;
use example.com/app/bindings/httpc as httpc;

struct Response {
    Status: i32,
    Body: str,
};

struct Client {
    h: *httpc.Client,

    fn Get(ctx: context.Context, url: str) Response! {
        var r = h.Get(ctx, url)?;
        return Response { Status: r.Status, Body: r.Body };
    };

    fn Close() void! {
        return h.Close();
    };
};

fn NewClient(base: str) Client! {
    var h = httpc.New(base)?;
    return Client { h: h };
};
```

App-код видит `Client`, `Response`, `NewClient`, `Get`, `Close`. Он не видит
`httpc` и `*httpc.Client`. `ctx` — обычное значение: facade принимает его и
передаёт в Go-метод. Если ctx не нужен, его нет в сигнатуре (см. §4).

### 3.2. Lifecycle

- Конструктор возвращает `T!`; zero value handle невалиден, если
  не сказано обратное.
- `Close` идемпотентен; повторный вызов не паникует.
- `Close` отменяет внутренние goroutine и снимает callbacks; после `Close`
  методы возвращают ошибку, а не работают с освобождённым ресурсом.
- Владелец handle — тот, кто вызвал конструктор. `par`-воркеры не делят
  один handle, если facade не объявил его thread-safe.
- В документации facade явно сказано: thread-safe или нет. По умолчанию —
  нет. «Наверное, безопасно» — не контракт.

### 3.3. Ошибки

- Go `error` → Ink `error`; facade возвращает `T!` или
  `void!`.
- `errors` запрещён в `.ink`: `check` создаёт, `?` пробрасывает, `on err`
  ловит. `errors.Is`/`errors.As` живут только в адаптере. App-код не должен
  знать Go-типы ошибок; если нужна классификация, facade отдаёт Ink-enum:

```hare
enum ErrorKind {
    NotFound,
    Timeout,
    Other,
};

fn Kind(err: error) ErrorKind { ... };
```

- Ошибку не сравнивают по строке. Строка — для сообщения, не для логики.
- Panic — не error. Адаптер не превращает panic в error молча; `on err` его
  не ловит, а `par` не восстанавливает: процесс падает со стеком и кодом 2.
  Если библиотека паникует на ожидаемом пути, это баг адаптера.
- Ошибка не теряется: `on err { ... }` либо обрабатывает, либо возвращает.
  Пустой handler запрещён правилом [syntax.md](../../vault/features/syntax.md).

### 3.4. Callbacks

- Callback-тип в facade — `fn(Event) void` или `fn(Event) bool`; ctx в него
  не передаётся неявно. Если callback нужен ctx, binding замыкает его внутри.
- Callback должен быть self-contained: не захватывать stack/worker-local
  состояние, которое умрёт до вызова. Если библиотека вызывает callback
  асинхронно, состояние живёт в binding и освобождается на `Close`.
- Lifetime регистрации документирован: синхронный callback, до `Close`,
  до первого события, с отменой.
- Callback не наследует deadline вызывающего: он приходит из goroutine
  библиотеки, а не из Ink-воркера. `spawn f()` в callback не переносит ctx.

## 4. Context

`context.Context` в Ink — обычное значение, а не скрытый параметр. Функция
принимает `ctx` явно только тогда, когда передаёт его в Go-API или выводит
deadline. Большинство функций его не принимает.

```ink
var ctx, cancel = context.WithTimeout(r.Context(), 2s);
defer cancel();

var u = loadUser(ctx, name)
    on err {
        http.Error(w, err.Error(), 500);
        return;
    };
```

На границе Go вариантов два:

1. **Explicit ctx** — Ink-функция принимает `ctx: context.Context` и передаёт
   его в Go-метод. В binding это обычный первый параметр.
2. **Без ctx** — если Go-API его не требует, его нет. Скрытого параметра и
   подстановки `context.Background()` нет.

`par` не создаёт, не отменяет и не выводит контекст. Отмена deadline не
останавливает воркеров: они доходят до конца. `par`-ветки захватывают `ctx`
лексически, как любую локальную переменную.

### 4.1. Где что происходит

| Ситуация | Что видит Ink | Что происходит на границе |
|---|---|---|
| Прямой вызов Go-функции с `ctx` | значение `ctx` | вызывающий передал его явно |
| Ink-метод реализует Go-интерфейс с `ctx` | метод с `ctx` в сигнатуре | Go-сигнатура совпадает, обёртки нет |
| Go вызывает Ink-callback | callback без `ctx` | ctx не передаётся; binding замыкает свой |
| `par { }` / `par for` | захваченный `ctx`, если он есть | ничего не подставляется |
| `spawn f(args)` | аргументы вызова | `ctx` передаётся только аргументом |
| Вызов через package boundary | `ctx` в сигнатуре | обычный параметр, переносится как значение |
| Вызов через function value | `ctx` в типе `fn(...)` | обычный параметр типа |

### 4.2. Правила

- Не хранить `context.Context` в struct. Контекст — параметр вызова, не
  поле.
- Не передавать `nil` вместо ctx.
- Не создавать `context.Background()` там, где уже есть deadline: это
  разрывает отмену. Если это нужно, это foreign layer и должно быть видно в
  адаптере.
- `context.Background()` уместен только на входе в программу, в новой
  goroutine, которой неоткуда взять ctx, или в обёртке, которую Go вызывает
  без ctx.
- Если Go-функция принимает ctx не первым параметром или прячет его в
  config-struct, это работа адаптера, а не app-кода.

## 5. Поддержанный Go-subset

### 5.1. Поддерживается

| Go | Ink | Условие |
|---|---|---|
| basic types, `string` | `i32`, `u64`, `f64`, `str`, ... | прямые |
| structs | struct | named fields; unexported — через конструктор |
| slices, arrays | `T[]`, `T[N]` | прямые |
| maps | `map[K, V]` | запись последовательная; `par for` по map нет; чтение в `par` — только если map неизменяем |
| pointers | `*T` | deref и поля можно; арифметики нет; в публичном API — opaque handle |
| simple interfaces | `interface` | method set из поддержанных сигнатур |
| function values | `fn(...)` | явные типы; `ctx` — обычный параметр типа |
| `error`, `(T, error)` | `T!` | любое число не-error результатов |
| `(T, bool)` | `var v, ok = ...` | не `or` |
| multiple results | `fn() A, B` | для Go-сигнатур; app API лучше struct |

### 5.2. Не обещается

| Не поддерживается как гарантия | Почему | Что делать |
|---|---|---|
| value-receiver interfaces | методы Ink — pointer receiver; value receiver получает копию, мутации теряются | адаптер; не выставлять такой интерфейс в app API |
| generic/variadic interface conformance | такие сигнатуры нельзя надёжно named/check; sema их пропускает, проверяет `go build` | адаптер + Go-test |
| ctx в callback | callback имеет Go-сигнатуру; ctx не передаётся неявно | callback без ctx или адаптер замыкает ctx |
| map range в `par for` | у map нет ord; порядок и победитель ошибки недетерминированы | запрещён sema; sequential range + slice |
| mutation через Go в `par` | анализатор видит вызов, а не эффект; указатель/интерфейс может менять общее состояние | trust boundary + `-race` |
| `sync`/atomic без явной модели | импорт запрещён в `.ink`; язык не знает lock discipline | `serve obj;` для app-объекта; adapter-owned lock для Go-состояния |
| cgo, `unsafe`, mutation через reflection | вне модели памяти и безопасности | отдельный binding, только если без этого нельзя |
| Go `init`/global state | порядок и побочные эффекты не контролируются | адаптер, который явно инициализирует |
| `chan`/`select` в app | вторая модель конкуренции; `par` и `spawn` — ключевые слова языка | адаптер |

### 5.3. Ошибки и несколько результатов

- `(T, error)` → `T!`.
- `error` → `void!`.
- `(T, bool)` → `var v, ok = f();`, не `or`: bool — не error.
- `(A, B, error)` — Go-форма. App-код может писать `(A, B)!` и
  `var a, b = f()?;`; для публичного API facade лучше struct, чтобы
  не плодить multi-result сигнатуры. Ограничение — на app API, не на
  грамматику.
- Ошибка из Go не становится panic; panic не маппится в обычный error.
  Panic — это Go panic: `on err` его не ловит, `par` не восстанавливает,
  процесс падает со стеком. Смешивать эти каналы — терять диагностику.

### 5.4. Интерфейсы

Ink реализует Go-интерфейсы структурно. Но:

- методы Ink — всегда pointer receiver; `*T` реализует интерфейс,
  value `T` — не всегда;
- Go-интерфейс с value receiver может скомпилироваться, но семантика будет
  копированием; не обещать;
- embedded interfaces, generic interfaces и variadic methods не входят в
  гарантированный subset;
- Go-интерфейс в публичном API facade — утечка. Оборачивать в Ink
  interface или opaque handle.

## 6. `par` safe subset

`par` проверяется статически. «Safe» здесь значит «разрешено правилами
анализа», а не «доказано отсутствие гонок». Полные правила — в
[PAR.md](PAR.md); здесь граница с Go.

### 6.1. Разрешено

- Чтение захваченных значений, которые никто не пишет.
- Чтение слотов slice/array, если ни один воркер не пишет этот root.
- Запись в disjoint slots: `base[i]`, `base[i].f`, `base[i][j]`, где
  `base` — slice/array, а внешний индекс содержит переменную итерации.
- Запись в локальные переменные воркера.
- Чтение захваченного map, если ни один воркер и ни один Go-вызов его не
  мутирует; Go-вызов здесь — trust boundary (§6.3).

### 6.2. Запрещено

- Запись в захваченный map — при любом ключе, даже «своём».
- Запись через захваченный указатель: `*p`, `p.f`, `p[i]`, non-pure `p.M()`.
- Вызов метода на захваченном интерфейсе: анализатор консервативно считает
  это записью.
- Запись в global.
- Запись в `self`.
- Запись внутри function literal: она не анализируется.
- Передача указателя/интерфейса в свободную Ink- или Go-функцию:
  эффект не отслеживается.
- `par for` по map: запрещён sema; сначала соберите ключи в slice.
- `chan`, `select` в app; `sync`, `sync/atomic` отвергаются импортом.
- `for ()` внутри `par` без гарантированного выхода: воркер может не
  завершиться, и `par` не дождётся.

Часть этих пунктов sema отвергает уже сейчас. Часть — контракт, который
компилятор не видит (function literals, Go-вызовы, mutation через
указатель). Второе не значит «разрешено»: это либо ошибка, либо §6.3.

### 6.3. Trust boundary

Есть случаи, где статический анализ не может ничего доказать: Go-функция
меняет состояние через указатель, callback пишет в захваченную структуру,
библиотека сама синхронизирует доступ. Это не повод притворяться, что
анализатор всё проверил.

Trust boundary — это **явная граница API**, а не аннотация в языке:

- функция живёт в `ffi/` или `bindings/`, не в домене;
- у неё есть контракт: что читает/пишет, блокирует ли, запускает ли
  goroutine, как отменяется;
- она вызывается из `par` только если контракт это разрешает;
- у неё есть тест, который гоняет конкурентные вызовы под `-race`;
- код-ревью смотрит на границу, а не на «оно скомпилировалось».

В app-коде указатели, интерфейсы, map, глобалы, `self` и function literals
с записью остаются запрещены. В адаптере они допустимы только как эта
граница: с контрактом и тестом, а не потому что «так скомпилировалось».

Компилятор такую функцию считает opaque call. Он не выдаёт «проверено» и
не должен. Если позже появится аннотация, она должна быть одна и та же для
всех trust boundary; пока её нет — граница видна по import graph и
контракту.

### 6.4. `sync` и atomic

Язык не предоставляет `sync`/atomic как часть модели и запрещает
`use sync;`/`use sync/atomic;` в `.ink`. Для app-объекта с общим состоянием
есть `serve obj;`: тип помечается served, каждый экземпляр несёт скрытый lock,
методы и свободные функции с `*T` сериализуются. Lock живёт внутри типа;
Go-специфику видит только runtime.
Если состояние принадлежит Go-библиотеке, lock остаётся в адаптере. Ждать
воркеры — `par`, отсоединять — `spawn`; у `spawn` нет join.

Канонические паттерны:

1. **Per-worker slots + последовательная свёртка.** 90% случаев. Никаких
   локов, никакого общего состояния.
2. **`serve obj;`** для app-объекта, который делят HTTP-хендлеры или `spawn`.
   Один lock на объект; части — отдельными объектами.
3. **Immutable snapshot + `atomic.Pointer[T]`.** Read-mostly конфиг в
   адаптере: публикация один раз, читатели не мутируют.
4. **Adapter-owned mutex.** Состояние принадлежит Go-библиотеке; facade
   отдаёт узкие методы. App-код не видит `sync.Mutex`.
5. **Atomic-счётчик с явным инвариантом.** Только если инвариант
   сформулирован и есть тест; не «на всякий случай».

Антипаттерны:

- `sync.Mutex` вокруг всего `par`, чтобы анализатор замолчал. Это
  сериализация, а не параллелизм.
- `sync`/atomic в app-коде, чтобы обойти запрет на запись в map/указатель.
  Это не обход, а смена модели владения; она должна быть в адаптере.
- «`-race` прошёл, значит безопасно». Детектор видит только выполненные
  пути; он не доказывает отсутствие гонок.
- «Sema пропустила, значит проверено». Sema проверяет только видимые
  записи; Go-вызовы и function literals — вне анализа.

### 6.5. `-race` как оракул

- `ink test -race`, `ink run -race`, `ink build -race` — штатный
  способ прогнать динамический детектор.
- CI для конкурентного кода запускает `-race` тесты; это условие приёмки,
  а не опция.
- `-race` не заменяет static checks и не делает их «sound». Он ловит то,
  что реально выполнилось.
- Ошибка в `par` детерминирована по ord для slice/array/str и C-style; для
  map — нет. Поэтому map в `par for` запрещён: тест может проходить
  сегодня и падать завтра.

## 7. Паттерны адаптера

### 7.1. Тонкий facade

Подходит для библиотеки без callbacks и lifecycle:

```hare
use example.com/app/bindings/markdown as md;

fn Render(src: str) str! {
    return md.Render(src);
};
```

App-код не знает, что внутри Go. Если завтра `md` заменят на Ink или
другую библиотеку, меняется только facade.

### 7.2. Go-binding с context

```go
package httpc

import "context"

type Client struct {
    // ...
}

func New(base string) (*Client, error)

func (c *Client) Get(ctx context.Context, url string) (*Response, error)

func (c *Client) Close() error
```

Ink-facade из §3.1 вызывает `h.Get(ctx, url)`; `ctx` — обычный параметр,
facade принимает его и передаёт дальше. `New` и `Close` не принимают ctx:
конструктор и освобождение не должны зависеть от deadline. Если `New` делает
сетевой запрос, это отдельный `Connect(ctx)` в адаптере.

### 7.3. Callback без ctx

```go
func (c *Client) OnEvent(fn func(Event))
func (c *Client) Close() error
```

- Callback вызывается из goroutine библиотеки.
- Ink-callback не получает ctx; deadline вызывающего не действует.
- Если callback нужен ctx, binding замыкает свой ctx внутри и передаёт
  его в Go-операции; Ink-сигнатура остаётся без ctx.
- `Close` снимает callback и ждёт завершения goroutine. Иначе callback
  может вызваться после освобождения состояния.

### 7.4. Ошибки как enum

```hare
enum NetError {
    NotFound,
    Timeout,
    Closed,
    Other { message: str },
};

fn Classify(err: error) NetError { ... };
```

App-код делает `match` по `NetError`, а не `errors.Is` по Go-типам.
Классификация — в адаптере, один раз.

## 8. Антипаттерны

- **Go-пакет в домене.** `use github.com/x/y` в `domain/*.ink` — граница
  уже протекла.
- **`context.Context` в публичной сигнатуре.** Даже если это удобно
  адаптеру, app-код не должен его видеть.
- **`if err != nil` в app-коде.** Это Go-форма; для одного результата —
  `or`, для multi-result — адаптер.
- **Go-указатель в публичном поле.** Opaque handle — да; `*http.Client` в
  домене — нет.
- **`spawn` вокруг callback.** Callback приходит из чужой goroutine;
  `ctx` и deadline туда не доходят.
- **`sync.Mutex` вместо модели владения.** Лок в app-коде не делает
  программу понятнее; он прячет, кто владеет данными.
- **Facade-переименование.** `fn Do() { goLib.Do(); };` с Go-типами в
  сигнатуре — не facade, а лишний слой.
- **`-race` как доказательство.** Это детектор, не verifier.
- **Оборачивание всего подряд.** `print`/`sprint` не нуждаются в facade;
  граница должна быть там, где есть состояние, lifecycle или Go-типы.

## 9. Пределы и открытые вопросы

- **Value-receiver интерфейсы.** Не обещаем. Если появится реальный
  сценарий, adapter должен доказать semantics копирования тестом.
- **Generic-интерфейсы.** Не обещаем conformance; `go build` — единственная
  проверка. Binding может спрятать их за не-generic API.
- **Callbacks с ctx.** Невидимого параметра нет: либо callback без ctx, либо
  адаптер замыкает ctx, либо binding владеет goroutine.
- **Map в `par for`.** Решено: sema error. Сначала последовательный range
  по ключам, затем `par for` по slice.
- **Отдельный Go-модуль для binding.** Плюс — версионирование; минус —
  `replace` и два `go.mod`. Решать по библиотеке, не по вкусу.
- **`-race` в CI.** Обязателен для конкурентного кода; не обязан для каждого
  локального билда.
- **cgo/unsafe.** Вне языка. Если адаптер без них не может — это
  исключение с отдельным ревью, а не «нормальный FFI».
- **Reflection.** Чтение типов — иногда нужно; мутация через reflection
  ломает модель `par` и не поддерживается.

## 10. Стены для сервисов

Три вещи, которые обычный сервис требует сразу, сегодня выражаются только
через binding; blank-импорт уже в языке, а фоновая задача — это `spawn f()`.
Это не баги: у каждой есть рабочая форма, но она стоит отдельного Go-пакета.
Решение о том, убирать ли стену из языка, принимает владелец языка; до тех
пор это цена входа.

| Что нужно | Почему не выражается | Рабочая форма |
|---|---|---|
| Имена JSON-полей | решено: `wire { Field: \"name\"; };` внутри struct | именованные виды `admin { ... }` для второго набора |
| Шаблоны и статика в бинаре | нет `//go:embed`: attributes вне языка | `os.DirFS` и файлы рядом с бинарём, либо binding с `embed.FS` |
| SIGTERM и graceful shutdown | нет `chan`; `signal.Notify` требует канал | binding: Go-пакет слушает сигнал и вызывает `srv.Shutdown` |
| Регистрация драйвера БД, `pprof`, `tzdata` | нужен blank-импорт | `use path as _;` — blank import |

Фоновая задача переживает обработчик через `spawn f(args)`, но пула, очереди и
ожидания нет: состояние передаётся аргументами, ошибка уходит в `on err`
области запуска.

Практическое следствие: зрелый сервис на Ink — это app-код плюс один
binding-пакет на каждую стену, которую он задевает. Пока стен три, это
дешевле, чем тащить Go-типы в домен; когда их станет больше, дешевле
пересмотреть язык.
