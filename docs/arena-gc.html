Арена Ink: почему GC вызывается 2–3 раза вместо 81

Короткий ответ: арена не отключает сборщик мусора и не просит его «не собирать». Она перестаёт создавать мусор в кадровом цикле. После первого кадра аллокаций нет вообще, поэтому счётчику кучи нечего двигать и GC просто не срабатывает.

81цикл GC на 240 кадров, когда память выделялась заново каждый кадр (Go-арена на кадр)
2–3цикла на те же 240 кадров с переиспользуемым буфером; все — до устойчивого режима
0циклов внутри кадрового цикла после первого кадра. На 480×270/60 кадров — 0 за весь прогон

1. Что видит пользователь

В Ink арена — это блок без имени. Внутри него new[T]() и T[](n) берут память из общего буфера, снаружи те же вызовы остаются обычными аллокациями Go.

for (var frame = 0; ...; frame += 1) {
    arena {
        var rows = Row[](H);        // Row = u8[480*4]
        go for (var y = ...; ...) {
            rows[y] = shadeRow(y, t);
        };
        for (var y = ...; ...) {
            copy(px[y * RowLen:], rows[y][:]);
        };
    };
};

Главное правило: память арены не покидает блок. Её нельзя вернуть, присвоить внешней переменной, передать в функцию, сохранить в defer или взять &T{}. Читать можно поле, индекс, len/cap и копировать скаляры наружу через copy.

Это ограничение — не побочный эффект, а доказательство: раз наружу ничего не утекло, буфер гарантированно мёртв на выходе из блока, и его можно отдать следующему выполнению того же блока.

2. Во что это превращается

Для примера tests/cases/arena_reuse компилятор печатает такой Go (сокращено):

var _s_scr1 _s_rt.Scratch[Point]   // один пул на тип
var _s_scr2 _s_rt.Scratch[int32]

for i := 0; i < 3; i += 1 {
    _s_mark4 := _s_d.Mark()

    _s_b5 := _s_scr1.Begin()                  // взять batch из пула
    _s_d.Push(func() { _s_scr1.End(_s_b5) })  // вернуть при любом выходе
    _s_b6 := _s_scr2.Begin()
    _s_d.Push(func() { _s_scr2.End(_s_b6) })

    {
        var p = _s_b5.New()          // bump внутри batch
        var xs = _s_b6.Slice(4, 4)   // bump внутри batch
        ...
    }

    _s_d.RunTo(_s_mark4)             // End: clear + вернуть в пул
}

_s_scr1.Release()                    // после цикла: отдать GC
_s_scr2.Release()

Обратите внимание на две вещи:

  • Scratch объявлен до цикла, а Release — после. Внутри цикла нет ни одного make: Begin только снимает готовый batch с полки.
  • Блок стоит после Mark(), а RunTo вызывает End. Поэтому return, break, continue и panic возвращают batch в пул, а не теряют его.

3. Путь от слова arena до памяти

Парсерarena { ... }; → ast.ArenaStmt. Обычный узел, без магии.
SemaСчитает глубину арены и отвергает всё, что может унести указатель наружу.
КодогенСобирает все new/make в блоке, по одному Scratch[T] на тип. В цикле поднимает объявление перед циклом.
РантаймScratch[T] — пул batch-ей. Batch — bump-аллокатор по []T.

4. Как устроен Scratch

Всё, что делает арену дешёвой, — это тридцать строк в runtime/source.go.

Scratch[Row] → batch #2 (free) batch #1 (free) пул свободных batch-ей, LIFO
Begin() → batch снимает последний; если пусто — создаёт пустой
batch.buf
выдано в этом выполнении (off) свободный хвост — будущий bump

Когда off + cap не влезает, буфер удваивается: make([]T, 2*len) + copy. Это происходит только на первых выполнениях, пока не достигнут high-water mark блока.

Четыре операции

ОперацияЧто делаетАллокация?
Begin()Берёт batch с полки пула или создаёт пустой Batch{}Нет (после прогрева)
Slice(n, cap)Сдвигает off на cap, обнуляет выдаваемый кусок через clearТолько если не хватает места
New()Slice(1,1), возвращает &s[0]Нет
End(b)clear(b.buf[:off]), off = 0, кладёт batch обратно в пулНет

Обнуление на выдаче — это то, что сохраняет семантику new и T[](n): каждое выполнение блока начинается с нулей, как будто память только что выделили. End обнуляет ещё раз, чтобы не держать ссылки на объекты в мёртвом буфере.

5. Почему это убирает вызовы GC

Go не запускает GC по таймеру. Он запускает его, когда счётчик выделенной кучи доходит до цели, вычисленной от живой кучи после прошлого цикла: примерно live × (1 + GOGC/100), при GOGC=100 — удвоение. Стартовая цель — около 4 MB.

Без переиспользования

Каждый кадр — новые 14.7 MB. Даже если они сразу становятся мусором, счётчик аллокаций растёт и каждые несколько кадров пробивает цель. Отсюда 81 цикл на 240 кадров: GC занят примерно каждым третьим кадром.

С ареной

Первый кадр выделяет 14.7 MB один раз. Дальше Begin/End только двигают off внутри уже существующего массива. Счётчик аллокаций стоит на месте, цель не достигается, GC нечего делать.

6. Когда именно были эти два вызова

Ни один из них не приходится на устойчивый кадровый цикл. Это прогрев и хвост программы. По шагам:

Старт процесса Инициализация рантайма, окно raylib, текстура, пакеты. Если стартовые аллокации пробили первую цель ~4 MB — здесь проходит GC №1.
Первый кадр Row[](H) впервые выделяет 14.7 MB. Это пробивает следующую цель — GC №2. Дальше буфер живёт в пуле и не выделяется.
Кадры 2–240 Только Begin, bump внутри buf, End, clear. Ноль make, счётчик кучи стоит. Ноль вызовов GC.
После цикла Release() отдаёт буфер, fmt/ teardown создаёт мусор. Возможен GC №3 — уже без влияния на кадры.

Отсюда два числа в замерах:

СценарийВсего GCГде именно
Постоянный буфер до цикла, 2.5K2выделение буфера на прогреве + fmt/хвост
Типизированный scratch, 2.5K3старт + первый кадр + fmt/хвост
Типизированный scratch, 480×2700весь прогон укладывается под цель GC
Честная оговорка. В репозитории сохранены только итоговые числа и пометка «из них startup/fmt», без лога номеров кадров. Раскладка по четырём фазам выше — механизм Go GC плюс форма кода; точные номера кадров в замере не записаны. Я воспроизвёл тот же паттерн отдельным Go-скриптом (14.7 MB batch, 240 итераций): GC случился ровно на кадре 1, дальше — ни одного; при выделении нового массива каждый кадр — 240 циклов. Это подтверждает механику, но не является повторным замером raylib-примера.

7. Почему Go-арена не дала этого эффекта

Первая версия использовала экспериментальный пакет arena из Go: arena.NewArena() на кадр и Free() на выходе. Ожидание было «зона без GC». Реальность:

  • чанки арены — обычные объекты кучи, и пейсер Go считает их аллокациями;
  • Free() не возвращает память сразу: полный чанк уходит в карантин и ждёт следующего GC;
  • пока карантин не разобран, следующая арена снова просит у кучи — счётчик растёт, GC запускается.

Итог: 81 цикл на 240 кадров. Арена уменьшила хвост по сравнению с полностью динамической кучей, но «нулём» не стала. Ноль даёт только переиспользование без аллокаций.

8. Чем вообще можно управлять GC в Go

Способы делятся на два класса: не создавать работу (лучший) и двигать порог (переносит работу, а не убирает).

ПриёмЧто делаетЦена
Переиспользовать буферы
арена, sync.Pool, xs[:0]		 Убирает аллокации в горячем цикле. Живая куча стабильна, цель GC не достигается. Почти нет; нужен явный жизненный цикл и аккуратность с указателями
Меньше живой кучи
value-типы, отказ от долгоживущих ссылок		 Цель следующего GC = live × 2. Меньше live — реже циклы и короче маркировка. Нет, это просто хороший код
GOGC=400
или debug.SetGCPercent		 Поднимает цель в 5 раз: GC реже, но каждый дороже по памяти и паузе. Пик RSS растёт; в пределе — OOM. Не лечит аллокации
GOGC=off + GOMEMLIMIT GC не запускается от процента, только при приближении к мягкому лимиту памяти. Годится для коротких batch-процессов; в долгом сервисе — риск
Pointer-free буферы Массив без указателей не сканируется: маркировка дешевле. Нет; Row = u8[1920] именно такой
Ballast (устаревший) Большой живой объект поднимает цель GC, как ручной GOGC. Заменён GOMEMLIMIT; память занята постоянно
runtime.GC() Принудительный цикл. Только добавить вызов, не убрать

Ink сознательно не трогает GOGC: это глобальная ручка процесса, она не делает код быстрее и не является свойством языка. Арена решает задачу в одном месте и не требует от пользователя знать про пейсер. GOGC остаётся доступен снаружи, как обычная переменная окружения — им можно пользоваться, но язык на него не опирается.

9. Скорость: 2–3 вызова GC — это ещё не C/Rust

Да, в текущей реализации это 2–3 вызова за весь прогон на 240 кадров, а не за кадр. В устойчивом режиме — ноль. Но из этого не следует, что программа стала такой же быстрой, как на C или Rust: число вызовов GC говорит только о том, что сборщик перестал быть узким местом.

Что реально дало снижение 81 → 2/3

Бэкендp50p99GC
Go-арена на кадр11.1 ms15.3 ms81
Переиспользуемый scratch10.9 ms13.7 ms3

Вызовов стало в 27 раз меньше, а p50 улучшился всего на 0.2 ms. Выигрыш — в хвосте (p99 минус 1.6 ms) и в освобождённом CPU: GC больше не отбирает ядра у кадров. Это важный вывод: 81 цикл выглядит страшно, но сам по себе не был главным тормозом. Основное время уходило в заполнение и копирование строк.

Прямое сравнение с C на том же цикле

Я собрал синтетический LUT-шейдер: 2560×1440, строка 10 KB, 240 кадров, один буфер на всё, 4 записи на пиксель. Одинаковая работа, одинаковый объём — 14.7 MB на кадр.

Вариантms/кадрGC за прогонскорость записи
Go, как в Ink: строка возвращается по значению + copy12.301.1 GB/s
Go, заполнение на месте через срез11.801.2 GB/s
Go, фиксированный массив-указатель (без bounds check)10.401.3 GB/s
C, gcc -O21.5–1.708.3–9.5 GB/s

Разница в 6–8 раз, и это не GC: у обоих ноль циклов. Причина — gcc автоматически векторизует побайтовый цикл (SIMD), а Go этого не делает. Go упирается в скалярные записи с проверками границ; C пишет блоками по 16–32 байта. Rust, скорее всего, оказался бы ближе к C: LLVM тоже умеет автовекторизацию, но я это не замерял — rustc на машине нет.

Как это читать. Это худший случай для Go: чистая вычислительная петля, идеально ложащаяся на SIMD. Реальный кадр ещё включает UpdateTexture, копирование и raylib, а исходный замер 2.5K — LUT-шейдинг, а не ровно этот цикл. Так что 6–8× нельзя переносить на всё приложение. Но и говорить «GC стал 3, значит скорость как в C» нельзя: разница в кодогенерации никуда не делась.

Что могло бы сократить разрыв: писать горячий цикл с явным SIMD (ассемблер или C-функция через FFI), убрать построчную копию и возврат строки по значению, либо оставить как есть и упираться в 60 fps с запасом. Последнее для 2.5K уже почти выполняется: 10.9 ms p50 при бюджете 16.7 ms.
