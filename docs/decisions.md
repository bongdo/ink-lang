# Decisions

## 2026-11-26 — `serve obj;`: lock на тип, а не на объект

**Контекст.** Флаг `_s_served` на объекте давал обходы: reassignment, фабрики,
holder’ы, глобалы в helper’ах. Каждый обход требовал новой проверки порядка, и
проверки начинали отвергать обычный код (глобальный store + helper без тестов).

**Решение.** `serve obj;` помечает тип; `sync.Mutex` есть в каждом экземпляре
served-типа, и методы/свободные функции с `*T` берут его безусловно. Флаг
`_s_served` удалён: `serve` — compile-time маркер, кодогенерации не даёт. Один
missed `serve` больше не гонка.

**Почему.** Тип уже некопируем из-за mutex, поля и так type-wide. Условный lock
не даёт гарантии, пока компилятор не докажет, что `serve` доминирует все
использования; это дорого и хрупко.

**Что отвергли.** Per-object флаг с проверками порядка/фабрик: много ложных
запретов и всё равно дыры через коллекции и helper’ы. Отдельный глобальный
реестр served-объектов: лишнее состояние.

**Цена.** Неserved экземпляры served-типа тоже платят за uncontended mutex.
`serve` перестаёт быть runtime-переключателем и становится маркером типа.

## 2026-11-26 — `serve obj;`: один скрытый lock на объект

**Контекст.** Запрет `sync` убрал единственный способ защитить объект от
конкурентных хендлеров. Go-адаптер оказался хаком: blind-web искал module path
и писал Go ради мьютекса.

**Решение.** `serve obj;` помечает конкретный struct-объект. В тип добавляются
скрытые `_s_mu sync.Mutex` и `_s_served bool`; `serve` ставит флаг. Вызовы
методов и свободных функций с `*T` проверяют флаг и берут lock. Из served-
метода вызывается raw-версия и held-версия свободной функции, без повторного
lock. Поля снаружи методов и `*T`-функций — ошибка. Копировать served-объект
нельзя; `go vet` ловит `copylocks`. Один объект — один lock; части — отдельные
объекты. `serve` нельзя в `par`/`spawn`, generic-типы не поддерживаются.

**Почему.** Go-код защищает поля структур, а не package-level переменные:
в stdlib и module cache mutex — поле структуры примерно в 90–95% случаев.
`par` не заменяет lock: он не объемлет HTTP-хендлеры и запрещает общую запись.

**Что отвергли.** `Shared<T>` с generic-синтаксисом. Handle-обёртку: ломает
свободные функции с `*T`. Package-level-only: противоречит Go-паттерну.
`spawn in q`: очередь защищает только тех, кто в неё пришёл. Owner-горутину:
медленнее, чем скрытый mutex, и не нужна для минимальной гарантии.

**Цена.** Один lock на объект сериализует и чтения; при нескольких
независимых группах нужна композиция. Свободные функции с глобальным served-
объектом могут только звать методы, не поля. Методы не должны возвращать
ссылки на внутренние slice/map/pointer; это документированный предел.

## 2026-11-25 — `par for`: чанки вместо горутины на итерацию

**Контекст.** `par for` создавал горутину на каждую итерацию. Для миллионов
мелких итераций это дороже самой работы, хотя одновременно жило не больше
`limit` горутин.

**Решение.** Для `par for` по slice/array (и простого C-style цикла) генератор
делит итерации на `limit` непрерывных чанков: одна горутина на чанк, внутри
цикл по итерациям. Каждая итерация сохраняет свой ordinal; `?` и `check`
добавляют ошибку с номером итерации и переходят к следующей, а не обрывают
чанк. `First()` по-прежнему выбирает низший ordinal. Тело с `defer`, `on err`,
вложенным `par`/`spawn`, `arena` или `return` идёт старым путём: горутина на
итерацию. Range по map и строке пока не чанкуется.

**Почему.** Число живых горутин ограничено `limit` при любом N; ментальная
модель «итерация — независимая единица» не меняется.

**Что отвергли.** Динамическую очередь с атомарным счётчиком: сложнее и пока
не нужна. Пул с переиспользованием горутин: чанки уже убирают основную цену.

**Цена.** Статические чанки могут дать перекос, если итерации разной
стоимости. `defer`/`on err`/вложенная конкурентность в теле остаются на
медленном пути. Ошибка внутри чанка не отменяет остальные итерации — это
сохраняет прежнюю семантику.

## 2026-11-25 — ошибки и конкурентность только средствами Ink

**Контекст.** `errors.New` конкурировал с `check` за конструктор, а `sync`
давал второй способ ждать и защищать общее состояние рядом с `par`/`spawn`.

**Решение.** `use errors;`, `use sync;`, `use sync/atomic;` и `fmt.Errorf` —
ошибка компиляции в `.ink` (коды `go-errors`, `go-sync`, `fmt-errorf`).
Создание ошибки — только `check(cond, "msg")`, проброс — `?`, обработка —
`on err`, классификация — Ink-enum или Go-адаптер. Ожидание — только `par`;
`spawn` отсоединяет и join не имеет. Общее состояние с локом живёт в Go-
адаптере; app-код `sync` не видит. Сгенерированный Go и адаптеры продолжают
пользоваться `errors`, `sync` и `fmt.Errorf` под капотом.

**Почему.** Один способ на намерение: импорт Go-пакета не должен быть
альтернативой конструкции языка. Пользователь не выбирает между `errors.New`
и `check`, `WaitGroup` и `par`, `Mutex` и моделью владения.

**Что отвергли.** Оставить `errors` как escape hatch — тогда правила ошибок
снова два. Оставить `sync.WaitGroup` для join у `spawn` — это второй способ
ждать; вместо него `par`. Разрешить `sync.Mutex` в app-коде — язык не умеет
проверять lock discipline.

**Цена.** `spawn` нельзя дождаться: незавершённую работу запускают через
`par`, а `spawn` — только fire-and-forget. Lock и классификация ошибок
требуют Go-адаптера. `go build -race` остаётся оракулом для адаптера.

## 2026-11-25 — ошибки: `?`, `on err`, `check` и `print`

**Контекст.** `or fail` давал три формы проброса и строку на каждый fallible-вызов;
`errors.New` конкурировал с `fail` за роль конструктора.

**Решение.** `T!`, `(A,B)!`, `void!` — единственная пометка. `call()?` возвращает
ошибку из текущей `!`-функции; на границе `par` она идёт в `ParErrors`, у
`spawn` — в обязательный обработчик. Функция без `!` тотальна: каждый
fallible-вызов обязан иметь `?`, `on err` или `_ =`. Ошибку рождает только
builtin `check(cond, "msg")`. `print(...)` — builtin уровня `fmt.Println`, без
ошибки. `or fail`, `or fail("ctx")`, `fail(err)`, `fail(err, "ctx")` удалены.

**Почему.** Три конструкции вместо девяти и 68 строк вместо 83 в одном демо
(−18%); уходит класс `if err != nil`; ошибка не может продолжить выполнение с
нулевым значением. `?` — один символ на вызов и полная видимость выхода на
месте вызова.

**Что отвергли.** B — оставить `or fail`: видимость выхода не окупает церемонию.
C — гибрид «оператор сам, выражение обработай»: правило зависит от позиции
вызова. Автовыброс `(T, error)` без `_ =`: возвращает тихие ошибки вида
`w.Write(b);`.

**Цена.** Нет контекста в Ink — обёртка только в Go-адаптере. `on err`
терминальный: «залогировать и пробросить» невозможно. Fallible-вызов в `defer`
теряет ошибку; правило не выбрано. `?` обязателен, поэтому автор помечает
каждый fallible-вызов.
