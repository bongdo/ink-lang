# 2.5K frame: что происходит сейчас

Замеры 2026-11-24, машина 4 ядра, Go 1.27, без `-race`. Код Ink не менялся:
это отдельный бенчмарк в `/tmp`, повторяющий форму `examples/frame` без raylib.

## Стенд

- 2560×1440, `Row = u8[10240]`, 240 кадров;
- `arena { rows = Row[](H); go for y ... limit 4 { rows[y] = shadeRow(y,f) }; copy(px, rows) }`;
- шейдер — арифметика на пиксель, без `sin`/`cos`, чтобы мерить не математику;
- raylib не подключён: `libraylib` и `xf86drm.h` на машине нет, дисплея нет.
  Поэтому нет `UpdateTexture` и draw, но кодогенерация `arena`/`go for` — та же.

## Текущий результат

| Что | p50 | p99 | max |
|---|---:|---:|---:|
| весь кадр | **7.9 ms** | 10.0 ms | 17–21 ms |
| shade (`go for`) | 7.2 ms | 9.6 ms | 11.5 ms |
| copy в `px` | 1.6 ms | 1.9 ms | 5.8 ms |

`limit 1` (один воркер): p50 **18.9 ms**. То есть параллельность работает:
4 воркера дают 2.4×, но не 4×.

GC: **2 вызова, оба до кадрового цикла**:

```
gc 1 @0.000s  14->14->14 MB, 14 MB goal, 4 P
gc 2 @0.003s  28->28->28 MB, 28 MB goal, 4 P
```

Первый — `px` (14.7 MB), второй — первый `rows` в арене (ещё 14.7 MB).
За 240 кадров — ноль. Это ровно те «два вызова» из прошлого разговора.

## Что в сгенерированном Go

`go for` — не один воркер, а **горутина на каждую строку** плюс семафор:

```go
for y := 0; y < H; y += 1 {
    _s_sem6 <- struct{}{}
    _s_i9 := y
    _s_ord8++
    _s_wg5.Add(1)
    go func() {
        defer _s_wg5.Done()
        defer func() { <-_s_sem6 }()
        var _s_d _s_rt.DeferStack
        defer _s_d.RunTo(0)
        rows[_s_i9] = shadeRow(_s_i9, f)
    }()
}
_s_wg5.Wait()
```

1440 горутин на кадр, 345 600 за прогон. Внутри каждой — свой `DeferStack`,
`WaitGroup`, семафор и `ParErrors`, хотя ошибок в теле нет.

Возврат строки — 10 KB копией:

```go
rows[_s_i9] = shadeRow(_s_i9, f)   // return Row + присваивание = 2 копии
```

Копирование в `px` получает `Mark`/`RunTo` на каждую строку, хотя деферов в теле
нет:

```go
for y := 0; y < H; y += 1 {
    _s_mark12 := _s_d.Mark()
    copy(px[y*RowLen:], rows[y][:])
    _s_d.RunTo(_s_mark12)
}
```

Если шейдер инлайнить в воркер, то же самое появляется **на каждый пиксель**:

```go
for x := 0; x < W; x += 1 {
    _s_mark11 := _s_d.Mark()
    ...
    _s_d.RunTo(_s_mark11)
}
```

Это 3.7 млн пар `Mark`/`RunTo` на кадр. Семантически они не нужны: тело не
кладёт ничего в `_s_d`, `RunTo` с текущей меткой — no-op.

## Сколько стоит каждая вещь

Я правил только сгенерированный Go в `/tmp`, компилятор не менял.

| Форма | p50 | p99 |
|---|---:|---:|
| как сейчас | 7.9 | 10.0 |
| убрать `Mark`/`RunTo` из copy-цикла | 7.25 | 9.4–11 |
| шейдер пишет в `&rows[y]` (copy elision), без меток | **6.0** | 8.0–8.7 |
| шейдер инлайном в воркере, без меток | 6.0 | 8.6–9.2 |
| то же + chunked `go for` на 4 воркера | **4.0** | 6.1–6.8 |
| как сейчас, `limit 1` | 18.9 | 20 |

Вклад по частям:

- горутина на строку + семафор: **~2.0 ms**;
- возврат 10 KB по значению + присваивание: **~1.3 ms**;
- `Mark`/`RunTo` на строку в copy-цикле: **~0.65 ms**;
- `Mark`/`RunTo` на пиксель при инлайне: **~3.4 ms** (8.86 → 5.43);
- параллельность 4 воркера: 18.9 → 7.9, **2.4×**.

## Вывод

- «Одна горутина» — наоборот: 1440 горутин на кадр, по одной на строку.
  Один воркер был бы 18.9 ms.
- До 6 ms p50 есть два дешёвых пути: copy elision для `rows[y] = shadeRow(...)`
  (6.0) или инлайн шейдера + починка меток (5.4–6.0).
- До 4 ms p50 и p99 ~6.3 — chunked `go for` поверх этого.
- Метки в циклах — общий баг кодогена, не только кадра: любой цикл в функции с
  `defer` платит `Mark`/`RunTo` на итерацию, даже если тело ничего не деферит.

## После реализации

В компиляторе: цикл без деферов больше не ставит `Mark`/`RunTo`; канонический
`go for` делится на `limit` воркеров с непрерывными диапазонами; копия строки
переносится в воркер; массивный результат функции пишется сразу в приёмник.
`Batch.Slice` больше не обнуляет буфер, это делает `End`.

| Что | p50 | p99 | GC |
|---|---:|---:|---:|
| до | 7.9 | 10.0 | 2 |
| после, с фазовыми таймерами (copy не фьюзится) | 3.8 | 6.4–6.7 | 2 |
| после, без таймеров между `go for` и copy | **3.1** | 4–7 | 2 |

Слияние четырёх байтовых записей в `u32` проверили и откатили: 1.46 против
1.47 ms, узкое место — память, а не число stores. Полный кадр с raylib
по-прежнему не измерен.

## Что не измерено

- raylib: `UpdateTexture`, draw, vsync — на этой машине не запускается;
- реальный LUT/`sin`-шейдер и 480p;
- полный кадр в приложении, а не синтетика.
