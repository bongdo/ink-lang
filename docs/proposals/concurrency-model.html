par {} vs общее состояние

par — это структурный параллелизм и join. Он не защищает общий store, в который лезут независимые HTTP-хендлеры. gated struct + gate store { } — одни ворота к объекту. Внешний store — отсутствие общего изменяемого состояния.

par {}

Каждый воркер пишет в свой слот. Общей записи нет, поэтому lock не нужен. Join ждёт всех и собирает результат.

par {}

Знаешь куски работы, запускаешь, ждёшь. Правило: не писать в общее. Это не синхронизация, это разделение.

gate store { }

У gated-объекта одни ворота. Вне gate объект не виден; копировать нельзя. Под капотом — mutex, но пользователь его не трогает.

Внешний store

Нет общего изменяемого состояния в памяти. Транзакции и сериализацию делает БД. Ни mutex, ни Go-адаптера.

Как это делают другие языки

PonyАкторы + reference capabilities. Компилятор доказывает отсутствие data race; локов нет вообще. Самая близкая «ментальная модель без lock».
Erlang / Elixir / GleamПроцессы с mailbox, изолированная память, состояние принадлежит процессу. Общего изменяемого store нет — есть owner-процесс.
Swift actorsactor изолирует mutable state; снаружи только async-вызов. Язык не даёт двум задачам войти в состояние одновременно.
Clojure / Haskell STMТранзакционная память: refs/TVar, atomically, retry. Общее состояние без явных lock, но с транзакциями.
Ada protected objectsЯзыковой объект с protected-операциями: mutual exclusion и barrier внутри типа. Ближайший аналог «synchronized object».
RustOwnership + Send/Sync. Гонок нет, но Arc<Mutex<T>> всё ещё виден; это не скрытая модель, а явная дисциплина.
