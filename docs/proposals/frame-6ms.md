# Кадр 2.5K за 6 ms: что можно сделать

Черновик предложения. Код не менялся. Числа — синтетический LUT-цикл на этой
машине (4 ядра, Go 1.27, gcc 15 `-O2`), если не сказано иное. Это не повторный
замер raylib-примера.

## Что уже известно

| Что | p50 | p99 | GC |
|---|---:|---:|---:|
| Go-арена на кадр, 2.5K | 11.1 ms | 15.3 ms | 81 |
| Переиспользуемый scratch, 2.5K | 10.9 ms | 13.7 ms | 3 |

Тот же объём работы в синтетике (2560×1440, 14.7 MB на кадр, 240 кадров):

| Вариант | ms/кадр | Комментарий |
|---|---:|---|
| Go, один поток, 4 записи на пиксель | 10.3 | совпадает с замером 10.9 |
| Go, `go for` как сейчас: горутина на строку + семафор | 4.7 | 1440 горутин на кадр |
| Go, 4 воркера по диапазонам строк | 2.7 | те же 4 ядра, без горутины на строку |
| Go, `u32`-запись + 4 воркера | 2.2 | одна запись на пиксель вместо четырёх |
| C, `gcc -O2`, один поток | 1.5–1.7 | SIMD-автовекторизация |
| `copy` 14.7 MB | 0.7 | 20.7 GB/s, копия не узкое место |
| `clear` 14.7 MB | 0.18 | двойной clear в `Batch` — 0.36 ms/кадр |

Главное наблюдение: 10.9 ms почти совпадает с **однопоточным** Go (10.3 ms).
Либо замер 2.5K был последовательным, либо `go for` в нём не работал, либо
шейдер тяжелее синтетики. Это первое, что нужно выяснить: от этого зависит,
нужен ли вообще SIMD.

С `-race` тот же параллельный цикл — 41.7 ms/кадр, в 15 раз медленнее. Если
бенчмарк собирался через `ink run --race`, число 10.9 ничего не значит.

## Вариант A. Сначала измерить (0.5 дня)

- собрать release-бинарник, без `-race`, без `SetTargetFPS`, без vsync;
- проверить `GOMAXPROCS` и квоту CPU (в контейнере может быть 1 ядро);
- разделить кадр на фазы: shade / copy / `UpdateTexture` / raylib;
- записать, используется ли `go for` и какой у него `limit`;
- прогнать с `GOGC=off` и без — должно быть одинаково, GC уже 0.

**Цена:** полдня. **Что даёт:** без этого все остальные числа — гадание.

## Вариант B. Форма кода и бэкенд (2–4 дня)

1. **Chunked `go for`.** Сейчас на каждую итерацию создаётся горутина и берётся
   семафор. Для числового диапазона можно поднять `workers` горутин и раздавать
   строки через `atomic`-счётчик. Замер: 4.7 → 2.7 ms. Это общий выигрыш для
   всех `go for`, не только кадра.
   **Цена:** аккуратно сохранить порядок ошибок, `break`/`continue`, `limit`,
   per-worker defer stack. Для map/range оставить старую схему.

2. **`u32`-пиксель.** Одна 32-битная запись вместо четырёх байтовых: 2.7 → 2.2 ms
   (серийно 10.3 → 8.3). Нужен пиксельный тип и байтовое представление для
   `UpdateTexture`; в Go это `unsafe.Slice`, в Ink — новый вид преобразования
   или FFI-функция.
   **Цена:** тип и граница FFI; без `unsafe` не обойтись.

3. **Заполнять строку на месте.** `rows[y] = shadeRow(y, t)` копирует 10 KB при
   возврате и ещё 10 KB при присваивании. Если писать сразу в `rows[y]`, минус
   ~0.7–1.4 ms. Сейчас sema запрещает передать аренный элемент в функцию,
   поэтому либо инлайнить тело в воркер, либо добавить copy elision для
   `arena`-присваивания.
   **Цена:** дублирование кода или новая оптимизация кодогена.

4. **Убрать двойной `clear`.** `End` уже обнуляет `buf[:off]`, `Slice` обнуляет
   ещё раз. Один clear лишний: −0.18 ms. Дёшево, но и выигрыш маленький.

Ожидание: 10.9 → 4–6 ms без SIMD и без C. Если замер был последовательным,
хватит одного chunked `go for`: 10.9 → ~4.7, уже под 6.

## Вариант C. SIMD или C-ядро (1–2 недели)

Вынести шейдер в C-функцию `shade_rows(px, y0, y1, t)` с `-O3 -mavx2` или в
Go-ассемблер. Замер C: 1.5–1.7 ms на весь кадр в одном потоке; с 4 воркерами
ещё меньше. Тогда 6 ms получаются с большим запасом, а не «впритык».

**Цена:** платформенная ветка (AVX2/NEON), cgo или asm, поддержка. raylib уже
тянет cgo/purego, так что новая категория зависимости не появляется, но
«чистый Go» заканчивается.

## Вариант D. GPU (2–4 недели)

Процедурный шейдер во фрагменте: CPU обновляет только униформы, пиксели считает
GPU. Время кадра падает до времени `DrawTexture` (<1 ms), 14.7 MB по шине не
ездят. Для настоящего рендера это правильный ответ; для демонстрации арены —
смена жанра, арена на CPU больше не нужна.

**Цена:** шейдеры, `LoadShaderFromMemory`, новая поверхность FFI, другой пример.

## Вариант E. Дешёвые продуктовые компромиссы

- считать в 1440p и растягивать на 2.5K — в 3 раза меньше пикселей;
- шейдить через строку и интерполировать — вдвое меньше работы, мыло;
- temporal reuse: переиспользовать прошлый кадр там, где сцена не менялась;
- если в шейдере всё ещё `sin`/`cos` на пиксель — заменить на LUT или
  рекуррентный шаг. Это может дать больше, чем весь SIMD.

**Цена:** качество или область применимости.

## Рекомендация

1. A — выяснить, последовательный ли замер и нет ли `-race`.
2. B1 — chunked `go for`, самый большой выигрыш на строку кода.
3. B2–B4 — по профилю.
4. C — если после B всё ещё >6 ms или нужен запас на 120 fps.
5. D — только если цель — реальный рендер, а не демо арены.

`GOGC`, `GOMEMLIMIT` и `runtime.GC()` не трогать: GC уже 0 в устойчивом режиме,
они ничего не дадут.

## Что вернуть после замера

- команду сборки и запуска;
- `GOMAXPROCS`;
- разбивку кадра по фазам;
- используется ли `go for` и с каким `limit`;
- p50/p99 без `-race`.

С этими пятью пунктами можно выбирать B или сразу C.
