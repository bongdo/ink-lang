# Arenas

## Что это

Блочная арена с невидимым аллокатором. Пользователь видит один блок; всё
остальное — фон:

```ink
arena {
    var p = new[Point]();
    var xs = make[i32](8);
};
```

- `new[T]()` и `make[T](n)` берут память из переиспользуемого типизированного
  буфера (пул на тип в пакете), снаружи это обычные Go-аллокации;
- буфер возвращается в пул на выходе из блока, включая return/break/continue и
  panic; память не освобождается, а переиспользуется;
- каждое выполнение блока начинается с нулей, поэтому `make`/`new` сохраняют
  семантику Go;
- после первого выполнения блок не аллоцирует: кадровый цикл не двигает
  `heap_live`, GC не запускается;
- `par` разрешён; `new`/`make` — только до `par` (воркер делит batch с циклом);
  воркер может открыть свою `arena { ... };`;
- память арены не покидает блок: sema отвергает присваивание
  captured-переменной, `return`, `&T{}`, аргумент/получатель вызова, `defer` и
  вызов метода на аренном значении;
- читать можно: поле, индекс, `len`/`cap`/`min`/`max`, копию структуры или
  массива без ссылок, `copy` наружу при скалярном элементе;
- воркер пишет аренный элемент по своему индексу (`rows[y] = row`); индекс из
  другого цикла отвергается как captured write;
- Go-арена и `GOEXPERIMENT` не используются.

Правило «арена не покидает блок» — не ограничение ради ограничения: именно оно
доказывает, что буфер можно переиспользовать, не боясь прочитать прошлый кадр.

## Замеры

2.5K, 240 кадров, 4 ядра, LUT-шейдинг, 14.7 MB строк на кадр:

| Бэкенд | p50 | p99 | GC-циклов |
|---|---|---|---|
| Go `arena` на кадр | 11.1 ms | 15.3 ms | 81 |
| типизированный scratch (сейчас) | 10.9 ms | 13.7 ms | 3 |

480×270, 60 кадров: 0 циклов GC. Остаток до 8.4 ms из спайка — форма кода
(возврат строки по значению и построчная копия), не бэкенд.

## Что показали замеры

2.5K, 240 кадров, 4 ядра, LUT-шейдинг, 14.7 MB строк на кадр:

| Буфер кадра | p50 | p99 | GC-циклов |
|---|---|---|---|
| `arena` на кадр | 11.1 ms | 15.3 ms | 81 |
| постоянный буфер до цикла | 10.2 ms | 13.2 ms | 2 |

Арена из Go считает аллокации обычными для пейсера, а полный чанк при `Free`
уходит в карантин до GC. Поэтому «арена = без GC» не выполняется: она даёт
меньше хвоста, чем куча на кадр, но не ноль. Настоящий ноль даёт только
переиспользование без аллокаций.

## Критерии приёмки

- `arena { new[Point](); make[i32](8); }` собирается без `GOEXPERIMENT` и без
  зависимости от экспериментального пакета Go.
- Повторное выполнение того же блока даёт нули: `tests/cases/arena_reuse`.
- Кадровый цикл на 2.5K не вызывает GC после прогрева (замер: 3 цикла на 240
  кадров, из них startup/`fmt`).
- `par for` внутри арены заполняет заранее выделенный буфер; результат
  совпадает с последовательным (`tests/cases/arena_par`).
- `new`/`make` внутри `par` внутри арены отвергаются sema.
- Воркер может открыть свою `arena { ... };`.
- Память арены не передаётся в функции: `f(p)` и `p.Move()` отвергаются.
- Кадр: строки в арене, `par for` по строкам, `copy` в постоянный буфер,
  upload вне блока (`examples/frame`).
- Память арены остаётся занятой на весь срок программы; это записано в SPEC.

## Открытые вопросы

- Байтовый слот (вариант B) для pointer-free блоков: один регион на блок и один
  `memmove` наружу. Делать по профилю, не раньше.
- `&T{}` внутри арены остаётся ошибкой; нужен ли heapify вместо неё?
- Нужны ли функции, принимающие арену, чтобы не инлайнить заполнение в воркер?
- Аллокация в `par` внутри арены запрещена из-за общего batch; нужен ли
  per-worker batch?
