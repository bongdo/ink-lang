# Errors

## Что это

Ошибка поднимается сама. `!` в результате говорит, что функция её пропускает;
`on err` — единственное место, где её ловят. Ни `or`, ни `fail` в языке нет.

```ink
fn loadConfig(path: str) Config! {
    check(path != "", "empty config path");
    var raw = os.ReadFile(path)?;
    var c = Config { Host: "", Port: 0 };
    json.Unmarshal(raw, &c)?;
    return c;
};

fn main() void! {
    var cfg = loadConfig("app.json");
    print("host:", cfg.Host);
};
```

- `T!`, `(A,B)!`, `void!` — единственная пометка fallibility.
- `call()?` возвращает ошибку из текущей `!`-функции. Поиск обработчика
  лексический: ошибка идёт по возвратам, а не по стеку вызовов. `?` можно
  ставить в любом выражении; в `void`-функции это ошибка компиляции.
- Функция без `!` тотальна: каждый fallible-вызов в ней обязан иметь `on err`
  или `_ =`.
- `on err { ... }` на месте обрабатывает одно выражение и оставляет zero
  value своего типа; слушатель (`on err` первым оператором функции или блока)
  ловит необработанные ошибки `par` и продолжает область.
- Внутри воркера `par` слушателя быть не может: ошибка воркера идёт в
  `ParErrors`, на join её получает слушатель, объемлющий сам `par`.
- `check(cond, "msg")` — единственный источник ошибки в app-коде.
- `print(...)` — builtin с семантикой `fmt.Println`, результат `void`; `_ =` для
  него не нужен.
- `_ = f();` — единственный явный выброс; нужен только для `(T, error)`-вызова,
  который стоит оператором.
- Контекст ошибки добавляет Go-адаптер (`fmt.Errorf("%w")`); в Ink обёртки нет.
- `errors.Is`/`errors.As` — инструмент адаптера, не app-кода; app-код
  классифицирует через Ink-enum.
- `panic(...)` — Go panic: `on err` его не ловит, `par` не восстанавливает.
- Удалены: `or fail`, `or fail("ctx")`, `fail(err)`, `fail(err, "ctx")`,
  `fail(errors.New(...))`, `on err { fail }`, `or return`, `or err`,
  `or panic`, `on fail`, `if err != nil { return err; }`.

## Критерии приёмки

- `var raw = os.ReadFile(path)?;` в `!`-функции компилируется и возвращает
  ошибку вызывающему; в `void`-функции `?` — ошибка компиляции с подсказкой.
- `f() or fail;` и `fail(err);` дают диагностику об удалённой форме:
  `or was removed; use ?`, `fail was removed; use check(...)`.
- `check(false, "x")` возвращает ошибку с текстом `x`; `check` в `void`-функции
  требует обработки.
- `print("a", 1);` компилируется без `_ =`, тип результата `void`.
- `on err` на месте оставляет zero value; слушатель ловит ошибку `par`;
  слушатель внутри воркера не компилируется.
- Тест ошибки пишется как `var cfg = loadConfig("") on err { failed = true; };`
  и проходит.
- Fallible-вызов голым оператором в `void`-функции отвергается; `_ = f();`
  разрешён.

## Открытые вопросы

- Fallible-вызов в `defer`: запретить (тотальность) или оставить известным
  пределом, как сейчас?
- `check(cond, "msg")`: только `str` или разрешить форматирование значения
  внутри сообщения?
- Нужен ли `err` в `on err`, если классификация всё равно в адаптере: остаются
  только `print(err)` и `panic(err)`.
- Имя `check`: `require` / `expect` читаются как проверка предусловия.
