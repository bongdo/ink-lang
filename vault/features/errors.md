# Errors

## Что это

Ошибка — не значение, которое автор обязан таскать вручную. Fallible-вызов
сам говорит, что может упасть; `or` решает, что делать.

```ink
var raw = os.ReadFile(path)
    or fail;
var cfg = parse(raw)
    or fail("bad config");
```

- `or fail` возвращает ошибку вызывающему;
- `or fail("ctx")` оборачивает её контекстом;
- `on err { ... }` — обработка на месте (после выражения) или слушатель
  области (первым оператором функции/блока), имя всегда `err`;
- внутри обработчика `fail(err, "ctx")` оборачивает и выходит; из слушателя
  области `return` нельзя, а `fail` поднимает ошибку в объемлющую функцию
  (в detached-задаче возвращаться некуда — паника);
- свежая ошибка: `fail(errors.New("msg"))` (`use errors;`); `error("msg")`
  отвергнут, `error` — только тип;
- `panic(...)` — Go panic: `on err` его не ловит, `go` не восстанавливает;
- `or return`, `or err`, `or panic`, `on fail` и
  `if err != nil { return err; }` отвергнуты.

## Критерии приёмки

- Слепой агент без документации чинит программу с `T or error` и `or return`
  по одним диагностикам.
- `fail("строка")` не проходит `ink check --fast`; `fail(errors.New("msg"))`
  проходит; `fail(error("msg"))` даёт `error-ctor` с подсказкой.
- `fail` в слушателе области поднимает ошибку в вызывающую функцию; в
  detached-задаче паникует.
- `or` в функции без `!` даёт ошибку с подсказкой.
- В `go`/`go for` `or fail` и `fail(...)` добавляют ошибку воркера, а не
  паникуют; на join её получает `on err` области или функция.
- Fallible-вызов голым оператором отвергается; `_ = f();` разрешён.
