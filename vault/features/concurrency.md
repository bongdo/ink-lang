# Concurrency

## Что это

Две конструкции и никакой скрытой многопоточности: `par` ждёт, `spawn`
отсоединяет. `sync` в app-код не входит.

```ink
par {
    a = loadA()?;
    b = loadB()?;
};

par for (var i = 0; i < len(xs); i += 1) limit 4 {
    out[i] = work(xs[i]);
};

spawn audit("saved") on err { print("audit:", err); };
```

- `par { }` — воркер на каждый top-level statement, join на блоке.
- `par for` — воркер на итерацию, `limit N` необязателен (по умолчанию
  `GOMAXPROCS`), тело итерации последовательное; range по map запрещён.
- `spawn f(args);` — отсоединённая задача, принадлежит программе и переживает
  вызывающую функцию; `f` возвращает `void` или `void!`; аргументы
  вычисляются до старта, замыкания нет. Join у `spawn` нет: если результат
  нужно дождаться, работа идёт через `par`.
- Ошибка задачи `spawn` обрабатывается на месте запуска:
  `spawn f(a) on err { ... };`. `void!` без обработчика — ошибка компиляции.
  Обработчик работает в задаче, видит только `err` и пакетные имена, не может
  `fail`/`return`/`?`; слушатель области ошибки отсоединённой задачи не
  получает.
- `on err { ... };` первым оператором функции/блока — слушатель
  необработанных ошибок `par`; после выражения — обработчик этого выражения.
  Слушатель не бывает пустым и не может использовать `return`.
- `par`/`par for` ждут все воркеры и не отменяют соседей; на join отдаётся
  ошибка с низшим ordinal — в слушатель области или из функции.
- `use sync;` и `use sync/atomic;` запрещены. Для общего состояния есть
  `serve obj;`: тип помечается served, каждый экземпляр несёт скрытый lock,
  методы и свободные функции с `*T` сериализуются. Поля снаружи внутренние,
  копировать тип нельзя. Один lock на тип; части — отдельными типами. Пропуск
  `serve` не гонка: lock берётся безусловно.
- Паника — Go паника: `on err` её не ловит, `par` не восстанавливает; процесс
  падает со стеком.
- Скрытого контекста нет: `ctx` — обычное значение, передаётся явно в те
  Go-API, которым он нужен. `within` удалён: дедлайн —
  `context.WithTimeout`.
- Fallible-вызов голым оператором запрещён: `f();` теряет ошибку, нужно
  `f()?`, `f() on err { }` или явное `_ = f();`.

## Критерии приёмки

- `par { }`, `par for ... limit N` и `spawn f(args);` проходят `ink check` и
  собираются.
- `par { }` и `par for` ждут всех воркеров; ошибка детерминирована по низшему
  ordinal; досрочной отмены нет.
- `spawn f()` переживает обработчик; `void!` без `on err` на вызове не
  компилируется; обработчик выполняется в задаче с ошибкой и не трогает
  локальные имена запускающей функции.
- У `spawn` нет join: ожидание выражается только `par`.
- `on err { }` первым оператором — слушатель; пустой блок и `return` дают
  ошибку.
- Паника не ловится `on err` и не заворачивается в `par`.
- `use sync;`, `use sync/atomic;`, `go`, `within`, `or err`, `or panic`,
  `on fail` отвергаются с подсказкой о новой форме.
- `serve c;` сериализует методы и свободные функции с `*Counter`; `par` может
  звать served-методы. Поля снаружи и копия served-типа отвергаются; lock есть
  у каждого экземпляра типа.
- `ctx` — обычное значение: нет `_ctx`-обёрток, нет цветных функций.
- Fallible-вызов голым оператором отвергается; `_ = f();` разрешён.
- `ink run -race` и `ink test -race` остаются динамическим оракулом.

## Открытые вопросы

- Пул/очередь в язык не входят: фоновая задача — `spawn f()`, а всё, что
  нужно дождаться, — `par`. Вернуться, если появится сценарий, который
  `par` не покрывает.
- Нужен ли отдельный handle/join у `spawn`? Сейчас нет: это был бы второй
  способ ждать.
